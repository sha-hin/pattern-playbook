The broken code

Scene 12’s importer saves every event of the feed, one by one, every time:

On Day 3 a feed had 20 events and this took milliseconds. A Booking.com feed of a busy cottage lists every closed night of the coming year: about 400 events. Each updateOrCreate() is a SELECT and, if anything differs, an UPDATE; almost always nothing differs, because the calendar didn’t change in 15 minutes. So a sync is ~400 queries to learn that nothing changed, about 1.5 seconds of a worker’s time.

The arithmetic: 3,100 feeds × 1.5 s ≈ 78 minutes of work every 15 minutes, for 4 workers that have 60. Every 15 minutes the scheduler queues all 3,100 again, so about 700 jobs more arrive than leave, and many are the same feed queued two or three times.

The fix, part 1: work out every change first, then write them together

The feed’s current blocks are loaded once. Each event in the new feed is compared in memory: unknown UID → new; known UID with other dates or kind → changed; identical → nothing. Blocks whose UID isn’t in the feed any more are removed. Only then does anything touch the database, in one short transaction: one upsert() for new and changed rows, one delete() for removed ones.

A feed that didn’t change, which is nearly all of them, costs one SELECT and no writes at all.

<?php

namespace App\Channels\Ical;

use App\Models\ExternalBlock;
use App\Models\IcalFeed;
use Illuminate\Support\Collection;
use Illuminate\Support\Facades\DB;

/** Everything one sync changes in a feed's blocks, collected first and written in one go. */
final class BlockChanges
{
    /** @var list<array<string, string|int>> rows to insert or update */
    private array $upserts = [];

    /** @var array<string, true> the UIDs the feed still contains */
    private array $seen = [];

    /** @param Collection<string, ExternalBlock> $current the feed's blocks now, by UID */
    private function __construct(
        private readonly IcalFeed $feed,
        private readonly Collection $current,
    ) {
    }

    public static function for(IcalFeed $feed): self
    {
        $current = ExternalBlock::query()
            ->where('property_id', $feed->property_id)
            ->where('source', $feed->source)                            // only this channel's blocks (scene 12)
            ->get()
            ->keyBy('uid');                                             // one query for the whole feed

        return new self($feed, $current);
    }

    /** Register one event of the new feed: new, changed or the same. Nothing is written yet. */
    public function seen(IcalEvent $event): void
    {
        $this->seen[$event->uid] = true;
        $block = $this->current->get($event->uid);

        $startsOn = $event->stay->checkIn->toDateString();
        $endsOn = $event->stay->checkOut->toDateString();

        if ($block !== null && $block->kind === $event->kind
            && $block->starts_on->toDateString() === $startsOn && $block->ends_on->toDateString() === $endsOn) {
            return;                                                     // identical: nothing to write
        }

        $this->upserts[] = [
            'property_id' => $this->feed->property_id,
            'source' => $this->feed->source->value,                     // raw rows: the enum's value, not the enum
            'uid' => $event->uid,
            'kind' => $event->kind,
            'starts_on' => $startsOn,
            'ends_on' => $endsOn,
        ];
    }

    /** Write every registered change in one short transaction. @return int the number of rows inserted, updated or deleted */
    public function commit(): int
    {
        $removedIds = $this->current
            ->reject(fn (ExternalBlock $block): bool => isset($this->seen[$block->uid]))
            ->pluck('id')
            ->all();

        if ($this->upserts === [] && $removedIds === []) {
            return 0;                                                   // the usual case: no transaction at all
        }

        DB::transaction(function () use ($removedIds): void {
            foreach (array_chunk($this->upserts, 500) as $rows) {       // a year of new blocks: still a few statements
                ExternalBlock::upsert($rows, uniqueBy: ['property_id', 'source', 'uid'], update: ['kind', 'starts_on', 'ends_on']);
            }

            if ($removedIds !== []) {
                ExternalBlock::whereKey($removedIds)->delete();
            }
        });

        return count($this->upserts) + count($removedIds);
    }
}

upsert() sends one INSERT … ON DUPLICATE KEY UPDATE for up to 500 rows. MySQL uses the unique index on (property_id, source, uid) from scene 12 to decide, row by row, whether it is an insert or an update. Eloquent’s upsert() also fills created_at and updated_at.

Model events don’t fire for an upsert() or a mass delete(). Nothing listens to ExternalBlock events, and this is the trade a bulk write always makes: write bulk only where nothing listens.

You just wrote the Unit of Work pattern

Unit of WorkKeep track of everything a business operation changes (new, changed and removed objects) and write all of it to the database at the end, in one go.

  • BlockChanges is a small Unit of Work for one sync: seen() registers each event as new, changed or unchanged; commit() works out the removals and writes everything in one transaction.
  • The win is not the transaction, which the old code also had. It is that comparing happens in memory, so writes happen only for real differences, and the writes that do happen are batched.
  • Doctrine’s EntityManager is a full Unit of Work: it tracks every entity you load, and flush() writes all their changes at once. Eloquent has none: save() writes immediately. So in Laravel you write a small, specific one, where a loop of saves is the bottleneck, like this one.

When not to use it

  • A handful of rows: a loop of save() calls is simpler, fires model events, and is fast enough. This sync was fine for months.
  • When other code listens to the model’s events (observers, scene 35): bulk writes skip them.

Laravel inside: what upsert() sends to MySQL

One statement for many rows. uniqueBy matters on databases that need to be told the conflict target; MySQL always uses the table’s unique indexes.

The broken code

The overlap guard is per feed. Two feeds of the same property are two keys, so their transactions run side by side on the same rows of the same index:

app/Jobs/SyncIcalFeed.php (the middleware, as part 1 left it)the bug
return [(new WithoutOverlapping("ical-feed-{$this->feed->id}"))->expireAfter(120)];   // the bug: per feed, while the rows are per property

Both transactions write external_blocks rows of the same property through the same unique index, (property_id, source, uid). To see why that can deadlock, you need to know what MySQL locks besides the rows themselves.

What REPEATABLE READ locks: rows and the gaps between them

MySQL’s default isolation level is REPEATABLE READ. Every plain SELECT in a transaction reads one consistent snapshot, taken at the first read, so the same query returns the same rows until commit. Locking reads and writes go further: to stop a phantom (a new row appearing inside a range you already read), InnoDB locks not only the index records it touches but also the gap before each one. A record plus its gap is a *next-key lock*.

Gap locks don’t conflict with each other: two transactions can hold the same gap. What waits for a gap lock is an insert into that gap. So two transactions that each hold a gap and each want to insert into the other’s gap wait for each other forever. InnoDB detects the cycle, rolls one back with error 1213, and lets the other finish.

INSERT … ON DUPLICATE KEY UPDATE (Laravel’s upsert()) takes an exclusive next-key lock on every duplicate it finds, and inserts the rest. Two batches for the same property, one per feed, each lock records and gaps around that property’s part of the unique index and insert new UIDs next to them: the pattern above, many times a minute.

See a gap lock yourself

Two mysql sessions on a copy of the database. Property 412 has blocks with UIDs a and c from Airbnb:

two mysql sessions (an experiment, not a test)
-- session 1
start transaction;
select id from external_blocks where property_id = 412 and source = 'airbnb' and uid = 'b' for update;   -- no row 'b': locks the gap between 'a' and 'c'

-- session 2
insert into external_blocks (property_id, source, uid, kind, starts_on, ends_on, created_at, updated_at)
values (412, 'airbnb', 'b', 'blocked', '2027-07-01', '2027-07-02', now(), now());                      -- waits: 'b' is inside the locked gap

-- session 3: who holds what
select engine_transaction_id, index_name, lock_mode, lock_status, lock_data
from performance_schema.data_locks where object_name = 'external_blocks';
-- … external_blocks_property_id_source_uid_unique  X,GAP                     GRANTED  412, 'airbnb', 'c', 77
-- … external_blocks_property_id_source_uid_unique  X,GAP,INSERT_INTENTION    WAITING  412, 'airbnb', 'c', 77

-- now repeat with session 1 at READ COMMITTED:
set transaction isolation level read committed;   -- before start transaction: the same select locks no gap, and the insert goes through

That last line is why "switch to READ COMMITTED" is a common reply to deadlocks. It removes gap locks for searches and index scans, but MySQL keeps them for duplicate-key checks, which is exactly what upsert() does. It would make these deadlocks rarer, not impossible, and it changes what every other transaction on the connection may see. The fix is to stop two writers meeting at all.

The fix: one sync per property at a time, and a retry for the rare deadlock left

The overlap key becomes the property. The second feed’s job finds the lock taken and is released back to the queue for 10 seconds; by then the first has committed. A property has at most three feeds, so the delay is seconds, and nothing waits on a lock inside MySQL.

Deadlocks can still happen elsewhere: a booking import (scene 15) can touch the same property. Laravel already knows what to do: DB::transaction($callback, attempts: 3) runs the callback again when the database reports a deadlock or a lost lock, and throws only after the third try. Retrying a deadlock is what MySQL’s message asks for; the transaction is all-or-nothing, so it is safe to run again.

There is no test for the retry. attempts: 3 is Laravel’s behaviour, not ours, and inside RefreshDatabase every transaction is nested in the test’s own, where Laravel deliberately rethrows a deadlock instead of retrying: only the outermost transaction can safely start again.
