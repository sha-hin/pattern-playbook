Observer

BehaviourGoF book

YouTube subscribe: the channel uploads once, every subscriber gets notified.

The rule to rememberWhen one thing happens and many things must react → fire an event; each reaction is its own listener.

Without it: the pain

register() calls the mailer, billing, CRM and analytics. Every new reaction means editing register().

With it: the fix

register() fires UserRegistered and knows nobody. A new reaction = a new listener.

Reach for it when you see

  • One method calls 4+ unrelated services after the main work
  • "Also, when X happens, we should…" keeps coming
  • The core action fails because a side-effect (email) failed

Real job where it fits

After sign-up: welcome email, start trial, sync CRM, track analytics. More coming.

Build it yourself: the full Observer pattern in plain PHP

No framework. Every part of the pattern is here, labelled with its role. Copy it, run it, change it.

SubjectRegistration keeps a list of observers and notifies them
ObserverRegistrationObserver the interface every reaction must follow
Concrete observersSendWelcomeEmail, StartFreeTrial, SyncToCrm

PHP has the same two interfaces built in: SplSubject and SplObserver.

<?php

declare(strict_types=1);

final class User
{
    public function __construct(public readonly int $id, public readonly string $email)
    {
    }
}

// ── Step 1: the Observer interface. Every reaction follows it. ──
interface RegistrationObserver  // Observer
{
    public function userRegistered(User $user): void;
}

// ── Step 2: the Subject. Keeps a list of observers and notifies them. ──
final class Registration  // Subject
{
    /** @var list<RegistrationObserver> */
    private array $observers = [];

    public function attach(RegistrationObserver $observer): void  // subscribe
    {
        $this->observers[] = $observer;
    }

    public function register(string $email): User
    {
        $user = new User(1, $email);                        // the real work (saving the user)
        $this->notify($user);

        return $user;
    }

    private function notify(User $user): void
    {
        foreach ($this->observers as $observer) {
            try {
                $observer->userRegistered($user);  // ring the bell, don't care who listens
            } catch (Exception $e) {
                // One broken reaction must not stop the others, but it must not be silent.
                echo '[error log] ' . get_class($observer) . ' failed: ' . $e->getMessage() . "\n";
            }
        }
    }
}

// ── Step 3: concrete observers. One class per reaction. ──
final class SendWelcomeEmail implements RegistrationObserver
{
    public function userRegistered(User $user): void
    {
        echo "Welcome email sent to {$user->email}\n";
    }
}

final class StartFreeTrial implements RegistrationObserver
{
    public function userRegistered(User $user): void
    {
        echo "14-day trial started for user {$user->id}\n";
    }
}

final class SyncToCrm implements RegistrationObserver
{
    public function userRegistered(User $user): void
    {
        throw new RuntimeException('CRM API timed out');    // broken today, on purpose
    }
}

// ── Using it ──
$registration = new Registration();
$registration->attach(new SendWelcomeEmail());
$registration->attach(new SyncToCrm());
$registration->attach(new StartFreeTrial());                // a new reaction = attach one more

$registration->register('ali@example.com');

Highlighted lines are the ones that make it this pattern. Run it: php examples/observer.php · Open the file on GitHub

Output
Welcome email sent to ali@example.com
[error log] SyncToCrm failed: CRM API timed out
14-day trial started for user 1

In a real Laravel project

The same pattern the way you would write it at work, using what the framework already gives you.

final class UserRegistered                                 // the event: just data
{
    public function __construct(public readonly int $userId) {}
}

public function register(array $data): User
{
    return DB::transaction(function () use ($data) {
        $user = User::create($data);
        event(new UserRegistered($user->id));  // ring the bell, know nobody
        return $user;
    });
}

final class SendWelcomeEmail implements ShouldQueue  // one reaction = one listener
{
    public bool $afterCommit = true;                     // never email a user that was rolled back
    public int $tries = 5;

    public function handle(UserRegistered $event): void
    {
        Mail::to(User::findOrFail($event->userId))->send(new WelcomeMail());
    }
}

// AppServiceProvider::boot() — a new reaction is one new line here
Event::listen(UserRegistered::class, SendWelcomeEmail::class);
Event::listen(UserRegistered::class, StartFreeTrial::class);
Event::listen(UserRegistered::class, SyncToCrm::class);

How Laravel builds it inside: Eloquent model observers: User::observe(UserObserver::class) attaches an object whose created(), updated()... methods run when the model is saved. Laravel registers them on its event dispatcher (see the Event Dispatcher card).
