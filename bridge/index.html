Bridge

StructureGoF book

TV remotes and TVs: any remote works with any TV because they’re designed separately.

The rule to rememberA class varies in two independent ways (what × how) → two hierarchies, one holds the other. A + B classes, not A × B.

Without it: the pain

InvoicePaidMail, InvoicePaidSms, OrderShippedMail, OrderShippedSms… every new channel multiplies the classes.

With it: the fix

A notification says WHAT. A channel decides HOW. One notification works on every channel.

Reach for it when you see

  • Class names that combine two words from two lists (PdfSalesReport)
  • Adding one option means adding N classes
  • Two things that change for different reasons

Real job where it fits

Many notification types (invoice paid, order shipped…) sent over mail, SMS, database, Slack.

Before: the code that hurts

final class InvoicePaidMail { /* ... */ }
final class InvoicePaidSms  { /* ... */ }
final class OrderShippedMail { /* ... */ }
final class OrderShippedSms  { /* ... */ }
// Slack arrives → InvoicePaidSlack, OrderShippedSlack, ...

Build it yourself: the full Bridge pattern in plain PHP

No framework. Every part of the pattern is here, labelled with its role. Copy it, run it, change it.

AbstractionNotification WHAT to say; it holds a Channel, and that link is the "bridge"
Refined abstractionsInvoicePaid, OrderDelayed
ImplementorChannel HOW to deliver
Concrete implementorsEmailChannel, SmsChannel

2 notifications + 2 channels = 4 classes cover all 4 combinations.

<?php

declare(strict_types=1);

// ── Step 1: the Implementor. HOW to deliver. ──
interface Channel  // Implementor
{
    public function deliver(string $to, string $subject, string $body): void;
}

final class EmailChannel implements Channel  // Concrete implementor
{
    public function deliver(string $to, string $subject, string $body): void
    {
        echo "EMAIL to {$to}\n  Subject: {$subject}\n  {$body}\n";
    }
}

final class SmsChannel implements Channel  // Concrete implementor
{
    public function deliver(string $to, string $subject, string $body): void
    {
        echo "SMS to {$to}: {$body}\n";                    // SMS has no subject line
    }
}

// ── Step 2: the Abstraction. WHAT to say. It HAS a channel. ──
abstract class Notification  // Abstraction
{
    public function __construct(protected readonly Channel $channel)  // the bridge between the two sides
    {
    }

    public function send(string $to): void
    {
        $this->channel->deliver($to, $this->subject(), $this->body());
    }

    abstract protected function subject(): string;

    abstract protected function body(): string;
}

// ── Step 3: refined abstractions. One class per message. ──
final class InvoicePaid extends Notification  // Refined abstraction
{
    public function __construct(Channel $channel, private readonly string $invoiceNo)
    {
        parent::__construct($channel);
    }

    protected function subject(): string
    {
        return "Invoice {$this->invoiceNo} paid";
    }

    protected function body(): string
    {
        return "Thank you, invoice {$this->invoiceNo} is paid.";
    }
}

final class OrderDelayed extends Notification  // Refined abstraction
{
    public function __construct(Channel $channel, private readonly int $orderId, private readonly int $minutes)
    {
        parent::__construct($channel);
    }

    protected function subject(): string
    {
        return "Order #{$this->orderId} is late";
    }

    protected function body(): string
    {
        return "Sorry, order #{$this->orderId} is about {$this->minutes} minutes late.";
    }
}

// ── Using it: any message x any channel, with no class per combination ──
$invoiceByEmail = new InvoicePaid(new EmailChannel(), 'INV-114');
$invoiceBySms = new InvoicePaid(new SmsChannel(), 'INV-114');
$delayBySms = new OrderDelayed(new SmsChannel(), 42, 15);

$invoiceByEmail->send('school@example.com');
$invoiceBySms->send('+201001234567');
$delayBySms->send('+201001234567');

// A WhatsApp channel = 1 new class, and every existing notification can use it.

In a real Laravel project

The same pattern the way you would write it at work, using what the framework already gives you.

final class InvoicePaid extends Notification              // WHAT to say: one class
{
    use Queueable;

    public function __construct(private Invoice $invoice) {}

    public function via(object $notifiable): array  // HOW: chosen per user, not per class
    {
        return $notifiable->prefers_sms ? ['vonage', 'database'] : ['mail', 'database'];
    }

    public function toMail(object $notifiable): MailMessage
    {
        return (new MailMessage)
            ->subject("Invoice #{$this->invoice->number} paid")
            ->line('Thank you, your payment was received.');
    }

    public function toVonage(object $notifiable): VonageMessage
    {
        return (new VonageMessage)->content("Invoice #{$this->invoice->number} paid. Thank you.");
    }

    public function toArray(object $notifiable): array
    {
        return ['invoice_id' => $this->invoice->id];
    }
}

$user->notify(new InvoicePaid($invoice));  // any notification × any channel

How Laravel builds it inside: Notifications. Your notification class says WHAT to send; via() lists the channels. Laravel looks up each channel class (mail, database, SMS...) and calls its send(), which asks your notification for toMail(), toArray()... Any notification works on any channel.
