When a survey closes, more things must happen

From Ahmed Nabil, Product Owner

When a survey closes: email the principal, start the comment analysis, notify the Ministry and write an audit log entry. Next month: clear the dashboard cache and send a summary to the school’s parents committee. And if the Ministry is down, the rest must still happen.

Why the quick fix is a trap

The quick fix puts every reaction inside close():

the quick fix (we won’t do this)
public function close(DateTimeImmutable $at): void
{
    $this->switchTo($this->status->close($at));

    $this->mailer->send($this->principal, /* ... */);
    $this->analysis->start($this->school);
    $this->ministry->notify($this->title);        // throws when the Ministry is down...
    $this->audit->write('survey closed', /* ... */);   // ...so this never runs
}

SurveyRun now depends on a mailer, an analysis service, the Ministry client and an audit log, none of which have anything to do with a survey’s lifecycle. Every new reaction edits it, and one failing reaction stops all the ones after it.

The survey only needs to announce what happened. Who reacts, and how, is somebody else’s business.

The pattern: Observer and Event Dispatcher

Remember itSomething happens and several unrelated parts must react → the subject announces it; observers subscribe and react, without the subject knowing them.

In the book’s Observer, a subject keeps a list of observers and notifies each one when something changes. An event dispatcher is a shared subject for the whole app: listeners subscribe to an event class (SurveyClosed), and anyone can dispatch an event without knowing who listens.

SurveyRun::close() now only records a SurveyClosed event (a small read-only object with the facts). The caller releases the recorded events and dispatches them. Each reaction is one small listener class, and the list of listeners lives in one place: bootstrap/app.php.

The dispatcher runs every listener even when one fails, and it never hides a failure: it logs it and returns it to the caller. Here the Ministry listener fails and the audit log is still written.

  1. 1The dispatcher

    Listeners are registered per event class, as a class name (built by the container only when the event happens) or a closure. Each listener runs inside its own try: a failure is logged, collected and returned, and the next listener still runs.

    src/Events/EventDispatcher.phpnew fileGitHub
    <?php

declare(strict_types=1);

namespace Evalu8\Events;

use Closure;
use Evalu8\Logging\Logger;
use Throwable;

/**
 * The shared subject: listeners subscribe to an event class, senders dispatch events,
 * and neither side knows the other.
 *
 * A failing listener never stops the others, and it is never silent: it is logged and
 * returned to the caller.
 */
final class EventDispatcher
{
    /** @var array<class-string, list<class-string|Closure(object): void>> */
    private array $listeners = [];

    /**
     * @param Closure(class-string): object $resolve builds listener classes on demand (the container's make())
     */
    public function __construct(
        private readonly Closure $resolve,
        private readonly Logger $logger,
    ) {
    }

    /**
     * @param class-string $eventClass
     * @param class-string|Closure(object): void $listener an invokable class (built when needed) or a closure
     */
    public function listen(string $eventClass, string|Closure $listener): void
    {
        $this->listeners[$eventClass][] = $listener;
    }

    /**
     * @return list<string> one line per listener that failed (empty when all succeeded)
     */
    public function dispatch(object $event): array
    {
        $failures = [];

        foreach ($this->listeners[$event::class] ?? [] as $listener) {
            $name = is_string($listener) ? $listener : 'closure';
            try {
                $callable = is_string($listener) ? ($this->resolve)($listener) : $listener;
                $callable($event);
            } catch (Throwable $e) {
                $failures[] = "{$name}: {$e->getMessage()}";
                $this->logger->warning('listener failed', ['event' => $event::class, 'listener' => $name, 'error' => $e->getMessage()]);
            }
        }

        return $failures;
    }
}

How Laravel does it

This is Laravel’s event system: Event::listen() (or listener discovery) subscribes listener classes to an event class, event(new SurveyClosed(...)) dispatches it, and listeners are built by the container. Listeners that implement ShouldQueue run in the background. Eloquent observers (Model::observe()) are the same idea for model events like created and updated.

Laravel
// A listener: Laravel finds it by the event type in __invoke() / handle()
final class EmailThePrincipal
{
    public function __construct(private Mailer $mailer) {}

    public function handle(SurveyClosed $event): void
    {
        Mail::to($event->principal)->send(new SurveyClosedMail($event));
    }
}

// Anywhere:
SurveyClosed::dispatch($title, $term, $school, $principal, $answers, now());

Check yourself

Answer in your head, then open the answer.

The parents committee must get a summary when a survey closes. What changes?

One new listener class and one listen() line in the bootstrap. SurveyRun doesn’t change.

Why does SurveyRun record events instead of dispatching them itself?

So it doesn’t depend on the dispatcher, and the caller can dispatch after everything is saved.

One listener throws. What happens to the others?

They still run. The failure is logged and returned, never hidden.

The analysis listener only logs. Doing the real analysis inside the request takes 40 seconds per school and times out.
