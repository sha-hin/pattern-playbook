Decorator

StructureGoF book

A phone case: it's still a phone, now it's also shockproof.

The rule to rememberAdd behaviour (cache, log, retry) around a class without editing it → wrap it in a class with the SAME interface.

Without it: the pain

To add caching you open a working, tested class and mix cache code into its SQL.

With it: the fix

A wrapper with the same interface adds caching, then passes the call inside. The original is untouched.

Reach for it when you see

  • You need caching / logging / retry around something that works
  • Constructor flags like $withCache, $withLogging
  • Different environments need different extras

Real job where it fits

School statistics take 3 seconds of SQL. You want a 10-minute cache, but not in local dev.

Before: the code that hurts

final class DbSchoolStats
{
    public function forSchool(int $schoolId): array
    {
        if (config('stats.cache') && Cache::has("stats:{$schoolId}")) {   // cache code mixed in
            return Cache::get("stats:{$schoolId}");
        }
        // ...heavy SQL...
    }
}

Build it yourself: the full Decorator pattern in plain PHP

No framework. Every part of the pattern is here, labelled with its role. Copy it, run it, change it.

ComponentSchoolStats the interface
Concrete componentDbSchoolStats the real, slow work; never edited
DecoratorsCachedSchoolStats, LoggedSchoolStats same interface, each wraps another SchoolStats
<?php

declare(strict_types=1);

// ── Step 1: the Component interface ──
interface SchoolStats  // Component
{
    /** @return array{school: int, average: int} */
    public function forSchool(int $schoolId): array;
}

// ── Step 2: the real work. We never edit this class. ──
final class DbSchoolStats implements SchoolStats  // Concrete component
{
    public int $queries = 0;

    /** @return array{school: int, average: int} */
    public function forSchool(int $schoolId): array
    {
        $this->queries++;
        usleep(20000);                                      // pretend this is a slow SQL query

        return ['school' => $schoolId, 'average' => 70 + $schoolId];
    }
}

// ── Step 3: a decorator. Same interface, wraps another SchoolStats, adds caching. ──
final class CachedSchoolStats implements SchoolStats  // Decorator #1
{
    /** @var array<int, array{school: int, average: int}> */
    private array $cache = [];

    public function __construct(private readonly SchoolStats $inner)  // wraps another SchoolStats
    {
    }

    /** @return array{school: int, average: int} */
    public function forSchool(int $schoolId): array
    {
        if (isset($this->cache[$schoolId])) {
            return $this->cache[$schoolId];  // added behaviour: answer from the cache
        }

        $result = $this->inner->forSchool($schoolId);  // otherwise pass the call inside
        $this->cache[$schoolId] = $result;                  // a real cache also sets an expiry time

        return $result;
    }
}

// ── Step 4: another decorator. Adds timing logs. ──
final class LoggedSchoolStats implements SchoolStats  // Decorator #2
{
    /** @var list<string> */
    public array $log = [];

    public function __construct(private readonly SchoolStats $inner)
    {
    }

    /** @return array{school: int, average: int} */
    public function forSchool(int $schoolId): array
    {
        $start = microtime(true);
        $result = $this->inner->forSchool($schoolId);
        $ms = round((microtime(true) - $start) * 1000, 1);

        $this->log[] = "school {$schoolId} answered in {$ms} ms";

        return $result;
    }
}

// ── Using it: stack the layers like a phone in a case in a pouch ──
$db = new DbSchoolStats();
$stats = new LoggedSchoolStats(new CachedSchoolStats($db));  // log → cache → database

$stats->forSchool(7);
$stats->forSchool(7);                                       // the cache layer answers this one
$stats->forSchool(9);

echo "Database queries: {$db->queries} (not 3)\n";
echo implode("\n", $stats->log) . "\n";

// No cache in local development? Simply don't wrap it: new LoggedSchoolStats($db).

Highlighted lines are the ones that make it this pattern. Run it: php examples/decorator.php · Open the file on GitHub

Output
Database queries: 2 (not 3)
school 7 answered in 20.1 ms
school 7 answered in 0 ms
school 9 answered in 20.1 ms

In a real Laravel project

The same pattern the way you would write it at work, using what the framework already gives you.

interface SchoolStats
{
    public function forSchool(int $schoolId): array;
}

final class DbSchoolStats implements SchoolStats { /* heavy SQL only, never edited */ }

final class CachedSchoolStats implements SchoolStats  // same interface...
{
    public function __construct(
        private SchoolStats $inner,  // ...holds one inside
        private \Illuminate\Contracts\Cache\Repository $cache,
    ) {}

    public function forSchool(int $schoolId): array
    {
        return $this->cache->remember(
            "school-stats:{$schoolId}",
            600,
            fn () => $this->inner->forSchool($schoolId),  // add caching, pass the call in
        );
    }
}

// AppServiceProvider
$this->app->bind(SchoolStats::class, DbSchoolStats::class);

if (! $this->app->isLocal()) {
    $this->app->extend(SchoolStats::class, fn (SchoolStats $stats, $app) =>
        new CachedSchoolStats($stats, $app['cache.store']));
}

How Laravel builds it inside: $this->app->extend(SchoolStats::class, fn ($stats) => new CachedSchoolStats($stats)) tells the container to wrap a service every time it is built. Each extend() adds one more layer.
