“Undo” in the survey editor

Memento

New ticket

“I changed the wrong question and can’t go back”

From Support desk

A coordinator turned a scored question into a comment by mistake. Turning it back didn’t restore the scale and the "scored" setting she had before, and she had to rebuild it from memory. Please add Undo and Redo to the question editor.

Why the quick fix is a trap

A first idea was an undo function that copies values out of the fields and back again:

the quick fix (we won’t do this)
$saved = [
    'text' => $editor->text->value,
    'type' => $editor->type->value,
    'max' => $editor->scale->max,
];
// ... later
$editor->text->value = $saved['text'];
$editor->type->value = $saved['type'];
$editor->scale->max = $saved['max'];
// forgot "scored"; didn't re-apply the editor's rules; the preview is now stale

The undo code has to know every field inside the editor and keep that list up to date; the next field added (or the one already forgotten) silently breaks undo. Writing the values back also skips the editor’s rules, so the preview and the enabled fields don’t match what is shown.

Only the editor knows its full state and how to put it back correctly. The rest of the app should just be able to say "save this moment" and "go back to it".

The pattern: Memento

Remember itYou need to save and restore an object’s state without exposing its internals → the object writes its own snapshot, someone else keeps the snapshots, and only the object can restore from one.

Three roles. The originator (QuestionEditor) can create a snapshot of itself and restore from one, re-applying its own rules. The memento (EditorSnapshot) is that saved state: immutable, so nobody can change it while it waits. The caretaker (History) keeps the snapshots in an undo stack and a redo stack, and never looks inside them.

Before each user change, History::record() saves a snapshot. Undo puts the current state on the redo stack and restores the previous one; a new change clears the redo stack, as in every editor. The stack has a limit, so a long session can’t grow memory forever.

In the book, the memento’s contents are hidden from the caretaker with language features PHP doesn’t have. Here immutability gives the same safety: the history can store and return a snapshot, but can’t alter it.

  3. 3The caretaker

    Two stacks and a limit. It calls snapshot() and restore() and never reads a snapshot’s contents.

    src/Editor/History.phpnew fileGitHub
    <?php

declare(strict_types=1);

namespace Evalu8\Editor;

/**
 * The Caretaker: keeps snapshots for undo and redo. It never looks inside them.
 */
final class History
{
    /** @var list<EditorSnapshot> oldest first */
    private array $undo = [];

    /** @var list<EditorSnapshot> */
    private array $redo = [];

    public function __construct(private readonly int $limit = 50)
    {
    }

    /**
     * Saves the current state, then applies a change made by the user.
     *
     * @param callable(): void $change
     */
    public function record(QuestionEditor $editor, callable $change): void
    {
        $this->undo[] = $editor->snapshot();
        if (count($this->undo) > $this->limit) {
            array_shift($this->undo);                       // forget the oldest step, keep memory bounded
        }
        $this->redo = [];                                   // a new change makes the old "future" invalid

        $change();
    }

    public function undo(QuestionEditor $editor): bool
    {
        $previous = array_pop($this->undo);
        if ($previous === null) {
            return false;                                   // nothing to undo: the button is disabled
        }

        $this->redo[] = $editor->snapshot();
        $editor->restore($previous);

        return true;
    }

    public function redo(QuestionEditor $editor): bool
    {
        $next = array_pop($this->redo);
        if ($next === null) {
            return false;
        }

        $this->undo[] = $editor->snapshot();
        $editor->restore($next);

        return true;
    }

    public function canUndo(): bool
    {
        return $this->undo !== [];
    }

    public function canRedo(): bool
    {
        return $this->redo !== [];
    }
}

How Laravel does it

Laravel has no Memento class, but Eloquent keeps one for every model: the attributes as they were loaded. getOriginal() returns them, isDirty() compares, and fill($model->getOriginal()) goes back. For undo across requests, store snapshots in the database (packages like spatie/laravel-activitylog save the before/after of every change).

Laravel
$question = Question::find(12);          // Eloquent remembers the loaded attributes
$question->type = 'text';
$question->scored = false;

$question->isDirty('type');              // true
$question->getOriginal('type');          // 'scale': the saved state

$question->fill($question->getOriginal());   // "undo" before saving
$question->isDirty();                    // false

Check yourself

Answer in your head, then open the answer.

A new field, "required", is added to the editor. What must change for undo to keep working?

The snapshot gets a required property, and snapshot() and restore() in the editor handle it. History doesn’t change.

Why does restore() call applyType() and refresh() instead of only setting values?

Restoring must leave the editor consistent: the enabled fields, the preview and the problems list depend on the values. Setting them without the rules was the bug of the quick fix.

Why does a new change clear the redo stack?

Redo means "go forward to a state that came after this one". After a new change, those states belong to a different history, so redoing them would mix two timelines.
