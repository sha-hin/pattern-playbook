The interview

System design of a channel manager: requirements, numbers, data model, flows, pushback, trade-offs; behavioural answers

#interviewThursday 14:00

Henrik · staff engineer (interviewer)We build software for holiday-rental hosts. Design a channel manager: a host connects each listing to Airbnb, Booking.com and Vrbo once, and from then on every booking, cancellation and price change flows between them. The one thing that must not happen is a double booking. You have 45 minutes. Talk me through it.

YouBefore I draw anything, can I ask a few questions about scale and what “must not happen” means when the channels themselves are involved?

Henrik · staff engineer (interviewer)Good. Go ahead.

Minutes 0–5: requirements, out loud

Ask, then write the answers on the board. The interviewer is checking that you build the right thing before you build it well.

FunctionalNon-functional
Connect a listing to each channel (OAuth, scene 13)No double bookings we could have prevented; the rest detected within a minute and handled
Import every reservation, change and cancellation (webhooks, polling fallback)A change reaches every channel within a minute
Push availability, minimum stays and prices to every channel after any changeNo lost reservation: every webhook stored before it is processed
Hosts see one calendar, liveSurvives a channel being down or rate limiting us for an hour
Book directly on our own site tooMulti-tenant: one host never sees another’s data

Say the uncomfortable fact early, because it shapes everything after it: we can’t make double bookings impossible. Airbnb can sell a night in the same second Booking.com does; neither asks us first. What we control is how short that window is, and what happens when it closes on a clash.

Minutes 5–10: numbers

Round numbers, said out loud, so the design is sized for something real:

QuantityEstimateWhat it decides
Properties50,000; 3 channels each → 150,000 listingsone MySQL primary holds this easily
Bookings20,000 a day ≈ 0.25/s average, ~5/s at peakwrites are not the problem
Calendar changeseach booking, cancellation, price or rule change → ~100,000 a dayeach one means a push to every other channel
Pushes100,000 × 2 other channels = 200,000 a day, in burstscoalescing per listing (scene 17), rate limits (scene 16)
iCal feeds (channels without an API)20,000 feeds every 15 minutes ≈ 22 per secondwrite only what changed (scene 37)
Searches~400/s on a busy eveningread replicas and indexes (scene 38), a search engine for text (scene 39)

The conclusion the numbers give you: this is not a big-data problem. It is a correctness and integration problem at moderate scale. A well-indexed MySQL with a replica, Redis and a queue is enough, and saying so is a senior answer.

FlowSteps
Inbound reservationWebhook → verify signature → store in webhook_events → 200 → queued job → lock the property → upsert by (channel, external_id) if the version is newer → coordinator (scenes 8, 14, 15)
The coordinatorOne class every calendar change goes through: record clashes, plan the cleaning, push to the other channels, update screens, write the partner message (scenes 18, 26, 31, 34)

Minutes 20–40: the pushback

This is the part that decides the interview. Each question has a short answer, a reason, and the failure it prevents.

Henrik asksYou answer
“Why not just lock the calendar across all channels before accepting a booking?”We can lock our own bookings (scene 4), but we can’t make Airbnb wait for our lock. So the design is: lock what we own, push fast so the channels’ windows are short, and detect clashes the moment a channel tells us (scene 18).
“Webhooks arrive out of order. A cancellation before the booking. Now what?”Every reservation carries the channel’s version or updated_at. We store the newest and ignore older ones, under the property lock, and a cancellation for an unknown booking is kept as a tombstone (scene 15).
“Airbnb is down for an hour. What breaks?”Nothing is lost: pushes retry with backoff until a deadline (retryUntil), and because each push sends the whole state, the first one that succeeds repairs everything. Inbound, the poller catches up from updated_since (scenes 15, 16).
“Why push the whole calendar, not the change?”A lost or reordered change leaves the channel wrong forever; a lost full push is fixed by the next one. And a burst of 200 changes becomes one push (scene 17).
“Why MySQL and a queue, not Kafka?”At ~5 writes a second there’s no throughput reason. The real risk is losing a message between the database and the queue, which the outbox solves without a new system. Kafka becomes worth it when many independent services consume the same events (scene 34).
“How do you know it works?”Contract tests per channel with recorded payloads and Http::preventStrayRequests(), a real concurrency test on MySQL for the lock (scene 4), load tests at a fixed arrival rate (scene 38), and the nightly reconciliation as the production check that the design holds.
“It grows 10×. What changes first?”The push volume, so more channels workers within each channel’s rate limit; then the replica count for reads. After that, every table is already keyed by account, so sharding by account is possible without rewriting queries (scene 19 made every query start from the account).

The behavioural round

Answer with real stories in four parts: the situation, what you did, the result with a number, and what you changed so it can’t happen again. One or two minutes each. These are written from the incidents in this course; in a real interview, use your own.

QuestionThe storyWhat it shows
“Tell me about a production incident you led.”Scene 42: the queue stalled. I read the kernel log first, saw the memory climb in a straight line, reproduced it in tinker, removed the static array, and wrote a blameless postmortem with five actions, including the alert that would have paged us at minute five instead of hour three.Method under pressure; fixing the system, not the symptom
“A time you disagreed with a decision.”Scene 33: the team wanted to cache nightly rates inside the pricing class, for speed. I argued that the price a guest pays must never come from a cache, and proposed a caching proxy used only by the quote page. We shipped it with a test proving bookings read the database.Disagreeing with reasons, offering an alternative
“A trade-off you made.”Scene 34: partner webhooks queued after commit were lost during a Redis failover. I chose an outbox: up to a minute of delay, and partners must ignore repeats, in exchange for never losing a message. I wrote the partner documentation for the two promises.Naming what you gave up
“How do you onboard or mentor someone?”Scene 43: I walked a new developer through one booking end to end, then the rules for where code goes, then the checks before a push. The architecture test we added that week caught a real race in her first review.Teaching with the real system
“A mistake you made.”Scene 36: an export I reviewed went out without the account scope. I didn’t see that it started from a different table. We reported the breach within 72 hours, and I designed the base export so a scope can’t be skipped again.Owning it, and fixing the class of bug

A good answer ends with what changed. "We fixed the bug" is a junior ending; "and now that kind of bug can’t ship, because…" is a senior one.
