DI Container

CreationNot in the book

A wall socket: your laptop doesn't build a power plant, it just plugs in.

The rule to rememberA class needs services → ask for them in the constructor; one place (the container) decides what you get.

Without it: the pain

The class builds its own mailer with new and env(). You can't test it without sending real emails.

With it: the fix

The class lists what it needs. The container passes them in; a test passes fakes.

Reach for it when you see

  • new SomeService() or Something::instance() inside methods
  • Tests that send real emails / hit real APIs
  • "Only one" handled by a static Singleton

Real job where it fits

An InvoiceSender needs a mailer and a logger. In tests you want a fake mailer.

Before: the code that hurts

    {
        $mailer = new SmtpMailer(env('MAIL_HOST'));   // hidden dependency, real email in tests

Build it yourself: the full DI Container pattern in plain PHP

No framework. Every part of the pattern is here, labelled with its role. Copy it, run it, change it.

ServiceInvoiceSender asks for what it needs in its constructor; never builds it
ContainerContainer knows how to build things and keeps shared instances
singleton()"build it once, then always give the same object"
Autowiringmake() reads the constructor and builds each dependency automatically
<?php

declare(strict_types=1);

interface Mailer
{
    public function send(string $to, string $subject): void;
}

final class SmtpMailer implements Mailer
{
    public function __construct(private readonly string $host)
    {
    }

    public function send(string $to, string $subject): void
    {
        echo "SMTP {$this->host}: '{$subject}' -> {$to}\n";
    }
}

final class FakeMailer implements Mailer                    // for tests: remembers instead of sending
{
    /** @var list<string> */
    public array $sent = [];

    public function send(string $to, string $subject): void
    {
        $this->sent[] = "{$to}: {$subject}";
    }
}

// ── Step 1: the service. It ASKS for a Mailer; it never creates one. ──
final class InvoiceSender  // Service
{
    public function __construct(private readonly Mailer $mailer)  // dependency injection
    {
    }

    public function send(int $invoiceId, string $email): void
    {
        $this->mailer->send($email, "Invoice #{$invoiceId}");
    }
}

// ── Step 2: the container ──
final class Container  // Container
{
    /** @var array<string, callable(): object> */
    private array $factories = [];

    /** @var array<string, object> */
    private array $shared = [];

    /** @param callable(): object $factory */
    public function singleton(string $name, callable $factory): void  // "build once, share it"
    {
        $this->factories[$name] = $factory;
    }

    public function make(string $name): object
    {
        if (isset($this->shared[$name])) {
            return $this->shared[$name];                    // already built: give the same object
        }

        if (isset($this->factories[$name])) {
            $this->shared[$name] = ($this->factories[$name])();

            return $this->shared[$name];
        }

        return $this->autowire($name);
    }

    /** @param class-string $class */
    private function autowire(string $class): object  // read the constructor, build what it needs
    {
        $constructor = (new ReflectionClass($class))->getConstructor();
        if ($constructor === null) {
            return new $class();                            // no constructor: nothing to inject
        }

        $arguments = [];
        foreach ($constructor->getParameters() as $parameter) {
            $type = $parameter->getType()->getName();       // e.g. "Mailer"
            $arguments[] = $this->make($type);  // build each dependency the same way
        }

        return new $class(...$arguments);
    }
}

// ── Using it: ONE place decides what "Mailer" means ──
$app = new Container();
$app->singleton(Mailer::class, function (): Mailer {
    return new SmtpMailer('smtp.example.com');
});

$sender = $app->make(InvoiceSender::class);                 // built automatically, Mailer injected
$sender->send(1001, 'school@example.com');

$same = $app->make(Mailer::class) === $app->make(Mailer::class);
echo 'Same Mailer each time? ' . ($same ? 'yes' : 'no') . "\n";

// ── In a test: no container needed, and no real email is sent ──
$fake = new FakeMailer();
$testSender = new InvoiceSender($fake);
$testSender->send(1002, 'test@example.com');
echo 'The fake mailer recorded: ' . $fake->sent[0] . "\n";

In a real Laravel project

The same pattern the way you would write it at work, using what the framework already gives you.

final class InvoiceSender
{
    public function __construct(  // ask, don't build
        private Mailer $mailer,
        private \Psr\Log\LoggerInterface $log,
    ) {}

    public function send(Invoice $invoice): void
    {
        $this->mailer->send($invoice->email, new InvoiceMail($invoice));
        $this->log->info('invoice.sent', ['invoice' => $invoice->id]);
    }
}

// AppServiceProvider: the ONE place that decides what Mailer means
$this->app->singleton(Mailer::class, fn () => new SmtpMailer(config('mail.host')));  // "only one", visibly

// Controller: Laravel builds InvoiceSender and fills its constructor
public function store(Invoice $invoice, InvoiceSender $sender) { $sender->send($invoice); }

// Test: no container needed, no real email
$mailer = new FakeMailer();
(new InvoiceSender($mailer, new \Psr\Log\NullLogger()))->send($invoice);
$this->assertCount(1, $mailer->sent);

How Laravel builds it inside: The service container. singleton() stores how to build something; make() uses PHP's ReflectionClass to read a class's constructor and builds every typed parameter, one level deeper each time. That is why type-hinting a class in a controller just works.
