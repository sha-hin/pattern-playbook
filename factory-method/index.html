Factory Method

CreationGoF book

A franchise: HQ owns the process, each branch decides its local product.

The rule to rememberA parent class runs a process that needs an object, but each child needs a different one → leave a create…() method for the child.

Without it: the pain

The base import has a switch on file extension to build the reader. A new format means editing the base class.

With it: the fix

The base calls createReader(). CsvImport and XlsxImport each return their own reader.

Reach for it when you see

  • A base class with a switch to decide which object to new
  • Subclasses that differ mainly in "which helper object"
  • "Add a new type" means editing the parent

Real job where it fits

Students can be imported from CSV or Excel. The import process is the same; only the file reader differs.

Before: the code that hurts

abstract class StudentImport
{
    public function run(string $path): void
    {
        $reader = match (pathinfo($path, PATHINFO_EXTENSION)) {   // the parent decides... badly
            'csv'  => new CsvReader($path),
            'xlsx' => new XlsxReader($path),
        };
        foreach ($reader as $row) { /* save */ }
    }
}

Build it yourself: the full Factory Method pattern in plain PHP

No framework. Every part of the pattern is here, labelled with its role. Copy it, run it, change it.

CreatorStudentImport runs the process, but leaves "which reader?" to its children
Factory methodcreateReader ) (abstract: each child decides what to create
Concrete creatorsCsvStudentImport, JsonStudentImport
ProductRowReader; Concrete products: CsvReader, JsonReader
<?php

declare(strict_types=1);

// ── Step 1: the Product and its concrete versions ──
interface RowReader  // Product
{
    /** @return list<array{code: string, name: string}> */
    public function rows(string $content): array;
}

final class CsvReader implements RowReader                  // Concrete product
{
    /** @return list<array{code: string, name: string}> */
    public function rows(string $content): array
    {
        $rows = [];
        foreach (explode("\n", trim($content)) as $line) {
            [$code, $name] = explode(',', $line);           // "S-1,Mona Adel"
            $rows[] = ['code' => $code, 'name' => $name];
        }

        return $rows;
    }
}

final class JsonReader implements RowReader                 // Concrete product
{
    /** @return list<array{code: string, name: string}> */
    public function rows(string $content): array
    {
        $rows = [];
        foreach (json_decode($content, true) as $item) {
            $rows[] = ['code' => $item['code'], 'name' => $item['full_name']];
        }

        return $rows;
    }
}

// ── Step 2: the Creator. The process is fixed; the reader is left to the children. ──
abstract class StudentImport  // Creator
{
    /** @var array<string, string> code => name */
    public array $students = [];

    public function run(string $content): int               // the process: same for every format
    {
        $reader = $this->createReader();  // "give me a reader", don't care which

        foreach ($reader->rows($content) as $row) {
            $this->students[$row['code']] = $row['name'];
        }

        return count($this->students);
    }

    abstract protected function createReader(): RowReader;  // the factory method
}

// ── Step 3: concrete creators. Each one decides which reader to create. ──
final class CsvStudentImport extends StudentImport  // Concrete creator
{
    protected function createReader(): RowReader
    {
        return new CsvReader();  // the child decides
    }
}

final class JsonStudentImport extends StudentImport  // Concrete creator
{
    protected function createReader(): RowReader
    {
        return new JsonReader();
    }
}

// ── Using it ──
$fromCsv = new CsvStudentImport();
echo 'CSV imported: ' . $fromCsv->run("S-1,Mona Adel\nS-2,Omar Said") . "\n";

$fromJson = new JsonStudentImport();
echo 'JSON imported: ' . $fromJson->run('[{"code":"S-3","full_name":"Laila Hassan"}]') . "\n";

// A new format (Excel) = one new creator + one new reader. StudentImport::run() never changes.

In a real Laravel project

The same pattern the way you would write it at work, using what the framework already gives you.

abstract class StudentImport
{
    final public function run(string $path): int             // the process: same for every format
    {
        $count = 0;
        foreach ($this->createReader($path) as $row) {  // "give me a reader", don't care which
            Student::updateOrCreate(['code' => $row['code']], ['name' => $row['name']]);
            $count++;
        }
        return $count;
    }

    abstract protected function createReader(string $path): iterable;  // the factory method
}

final class CsvStudentImport extends StudentImport
{
    protected function createReader(string $path): iterable
    {
        return new CsvRowReader($path);  // the child decides
    }
}

final class XlsxStudentImport extends StudentImport
{
    protected function createReader(string $path): iterable
    {
        return new XlsxRowReader($path);
    }
}

How Laravel builds it inside: Laravel's Manager base class (behind sessions, hashing, notifications) runs the same process for every driver and calls a factory method that each child class supplies: SessionManager has createFileDriver(), createDatabaseDriver(), createRedisDriver()...
