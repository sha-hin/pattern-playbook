Your system shows the term as closed, but our API has no record of the results. Your logs show a deployment restart at the same minute. We need a guarantee: if the term is closed on your side, we receive the results, even if our API is down for a while.

Why the quick fix is a trap

Closing a term saved the results, then called the Ministry:

the quick fix (we won’t do this)
$this->store->saveAndClose($term, $results);       // committed to our database
// ← a restart here, and the Ministry is never told
$this->ministry->publishResults($term, $results);   // or: the Ministry is down, and this throws

Two systems, two separate steps, and no way to make them succeed or fail together. Swapping the order is no better: the Ministry could receive results that our database then fails to save.

The fix has two parts. First, save everything this operation changes, including a record of the message the Ministry must receive, in one database transaction. Second, let a separate process deliver that message, and keep trying until it succeeds.

The pattern: Unit of Work and Transactional Outbox

Remember itAn operation changes several things and must tell another system → collect every change in a unit of work, commit them in one transaction together with an outbox message, and let a relay deliver the message.

Unit of Work (Fowler, *Patterns of Enterprise Application Architecture*): TermClosing registers the closed term, each frozen result and the outbox message; commit() writes them all in one transaction. If any write fails, nothing is saved.

Transactional Outbox: the message to the Ministry is just another row, in the outbox table, saved in that same transaction. If the term is closed, the message exists. The request never calls the Ministry.

The relay runs every minute: it sends pending messages, marks them sent, retries failures and raises an alert when it gives up. Delivery is at least once: a crash after sending but before marking can send a message twice, so each message carries an idempotency key and the receiver ignores repeats.

Neither pattern is in the Gang of Four book.

  2. 2The Unit of Work

    registerNew() refuses a class it has no mapper for immediately, not at commit time. commit() writes everything in one transaction and rolls back on any failure.

    src/Persistence/UnitOfWork.phpnew fileGitHub
    <?php

declare(strict_types=1);

namespace Evalu8\Persistence;

use LogicException;
use PDO;
use Throwable;

/**
 * Unit of Work: collects every change of one business operation, then writes them all
 * in ONE database transaction on commit(). Either everything is saved, or nothing is.
 */
final class UnitOfWork
{
    /** @var list<object> */
    private array $new = [];

    /**
     * @param array<class-string, Mapper> $mappers which mapper writes which class
     */
    public function __construct(
        private readonly PDO $db,
        private readonly array $mappers,
    ) {
    }

    public function registerNew(object $entity): void
    {
        if (!isset($this->mappers[$entity::class])) {
            throw new LogicException('No mapper for ' . $entity::class . '.');   // fail now, not at commit
        }

        $this->new[] = $entity;
    }

    public function commit(): void
    {
        $this->db->beginTransaction();

        try {
            foreach ($this->new as $entity) {
                $this->mappers[$entity::class]->insert($entity);
            }
            $this->db->commit();
        } catch (Throwable $e) {
            $this->db->rollBack();                          // nothing from this operation is kept
            throw $e;
        } finally {
            $this->new = [];
        }
    }
}

  12. 12The Ministry API stand-in

    Down for its first call, and idempotent: it ignores a key it has already received.

    fakes/Ministry/Client.phpnew fileGitHub
    <?php

declare(strict_types=1);

namespace Ministry;

use RuntimeException;

/**
 * Stand-in for the Ministry of Education's results API. It is down for its first N calls,
 * and it ignores a message key it has already received (it is idempotent).
 */
final class Client
{
    /** @var array<string, true> */
    private array $received = [];

    public function __construct(private int $outagesLeft = 1)
    {
    }

    /** @param array<string, mixed> $payload */
    public function publishResults(string $idempotencyKey, array $payload): void
    {
        if ($this->outagesLeft > 0) {
            $this->outagesLeft--;
            throw new RuntimeException('503 Service Unavailable');
        }

        if (isset($this->received[$idempotencyKey])) {
            echo "  Ministry: already have {$idempotencyKey}, ignored\n";

            return;
        }

        $this->received[$idempotencyKey] = true;
        echo '  Ministry: received ' . count($payload['results']) . " results for {$payload['term']}\n";
    }
}

  13. 13The relay

    Pending messages are sent in order. A failure counts an attempt; after maxAttempts the message is marked failed with an ALERT. Nothing is dropped silently.

    src/Outbox/OutboxRelay.phpnew fileGitHub
    <?php

declare(strict_types=1);

namespace Evalu8\Outbox;

use Evalu8\Logging\Logger;
use Ministry\Client;
use PDO;
use Throwable;

/**
 * The relay: a worker (run every minute by the scheduler) that sends pending outbox messages,
 * retries failures, and raises an alert when it gives up. Messages are never lost or silent.
 *
 * Delivery is "at least once": if the relay crashes after sending but before marking the row
 * as sent, the message is sent again. The receiver must ignore repeats (by message key).
 */
final readonly class OutboxRelay
{
    public function __construct(
        private PDO $db,
        private Client $ministry,
        private Logger $logger,
        private int $maxAttempts = 5,
    ) {
    }

    public function run(): void
    {
        $pending = $this->db->query("SELECT * FROM outbox WHERE status = 'pending' ORDER BY id")->fetchAll(PDO::FETCH_ASSOC);

        foreach ($pending as $row) {
            try {
                /** @var array<string, mixed> $payload */
                $payload = json_decode((string) $row['payload'], true, flags: JSON_THROW_ON_ERROR);
                $this->ministry->publishResults((string) $row['message_key'], $payload);

                $this->db->prepare("UPDATE outbox SET status = 'sent', attempts = attempts + 1 WHERE id = ?")->execute([$row['id']]);
                $this->logger->info('outbox message sent', ['key' => $row['message_key']]);
            } catch (Throwable $e) {
                $attempts = (int) $row['attempts'] + 1;
                $status = $attempts >= $this->maxAttempts ? 'failed' : 'pending';
                $this->db->prepare('UPDATE outbox SET status = ?, attempts = ?, last_error = ? WHERE id = ?')
                    ->execute([$status, $attempts, $e->getMessage(), $row['id']]);

                $status === 'failed'
                    ? $this->logger->warning('ALERT outbox message failed for good', ['key' => $row['message_key'], 'error' => $e->getMessage()])
                    : $this->logger->warning('outbox message failed, will retry', ['key' => $row['message_key'], 'attempt' => $attempts, 'error' => $e->getMessage()]);
            }
        }
    }
}

How Laravel does it

With the database queue driver, a queued job is a row in the jobs table. Dispatch a job inside DB::transaction() on the same connection and the job row is saved in the same transaction as your data: the jobs table becomes your outbox and queue:work is the relay. DB::afterCommit() and ShouldQueueAfterCommit cover the opposite case: never queue for data that was rolled back.

Eloquent has no Unit of Work (Doctrine’s EntityManager::flush() is one); DB::transaction() around your writes plays that role.

Laravel
DB::transaction(function () use ($term, $results): void {
    ClosedTerm::create(['term' => $term, 'closed_at' => now()]);
    foreach ($results as $result) {
        TermResult::create(/* ... */);
    }

    // database queue on the same connection: this row commits with the data above
    PublishResultsToMinistry::dispatch($term, idempotencyKey: "ministry-results:{$term}");
});

Check yourself

Answer in your head, then open the answer.

The server restarts right after the commit. Is the Ministry message lost?

No. It is a row in the outbox, committed with the results. The relay sends it on its next run.

Why must the Ministry ignore a message key it has already seen?

Delivery is at least once: the relay can crash after sending and before marking the row as sent, and then sends it again.

What does the Unit of Work guarantee?

Every change registered in one operation is saved in one transaction: all of them, or none.
