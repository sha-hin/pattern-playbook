Move from the OpenAI SDK to a local LLM

Adapter

New ticket

Use a real language model for comment analysis, on our own server

From Ahmed Nabil, Product Owner, and the legal team

Keyword matching misses too much. Use a language model. We prototyped with OpenAI, but legal says comments about named teachers must stay on our servers, so production will use our self-hosted Ollama server. We may need OpenAI again for schools that allow it.

Why the quick fix is a trap

The two SDKs could not be more different. Calling them directly from TermReport looks like this:

the quick fix (we won’t do this)
if ($provider === 'openai') {
    $response = $openai->chat()->create([
        'model' => 'gpt-4o-mini',
        'messages' => [['role' => 'user', 'content' => $prompt]],
    ]);
    $summary = $response->choices[0]->message->content;
} else {
    $result = $ollama->generate(['model' => 'llama3.2', 'prompt' => $prompt]);
    if (isset($result['error'])) { /* ...Ollama doesn't throw, it returns an error... */ }
    $summary = $result['response'];
}

Now TermReport knows two vendors’ method names, two result shapes and two ways of failing (OpenAI throws ErrorException; Ollama returns ['error' => ...]). Every other place that needs a summary copies this block, and a third provider adds a third branch everywhere.

We already have the interface we *want*: CommentAnalyzer::summarize(array $comments): string. The SDKs just don’t have that shape, and we can’t edit them: they are someone else’s code.

The pattern: Adapter

Remember itA class you can’t change has the wrong interface → wrap it in a small class that implements YOUR interface and translates every call, result and error.

An adapter is a travel plug: your charger (our code) stays the same, the wall socket (the SDK) stays the same, and the plug in between makes them fit.

OpenAiCommentAnalyzer and OllamaCommentAnalyzer both implement CommentAnalyzer. Each one holds the vendor’s client object and translates three things: our call into their call, their result into our string, and their failure into our exception (AnalysisFailed). The rest of the app never sees a vendor class.

Compare it with the Decorator (chapter 9): a decorator wraps something that already has *our* interface and adds behaviour. An adapter wraps something with the *wrong* interface and adds nothing: it only translates.

  2. 2Ollama: a different shape

    Ollama’s API takes and returns arrays, and reports errors as an error key instead of throwing.

    fakes/Ollama/Client.phpnew fileGitHub
    <?php

declare(strict_types=1);

namespace Ollama;

use FakeLlm\Model;

/**
 * Shaped like Ollama's HTTP API (POST /api/generate): an array in, an array out.
 * Errors come back as ['error' => '...'] instead of an exception.
 */
final readonly class Client
{
    /** @param list<string> $installedModels */
    public function __construct(private string $host, private array $installedModels = ['llama3.2'])
    {
    }

    /**
     * @param array{model: string, prompt: string, stream?: bool} $request
     * @return array{model?: string, response?: string, done?: bool, error?: string}
     */
    public function generate(array $request): array
    {
        if (!in_array($request['model'], $this->installedModels, true)) {
            return ['error' => "model \"{$request['model']}\" not found, try pulling it first"];
        }

        return ['model' => $request['model'], 'response' => Model::reply($request['prompt']), 'done' => true];
    }
}

  5. 5The same question for every model

    Both adapters send the same instruction, so switching provider doesn’t change what is asked.

    src/Analysis/CommentPrompt.phpnew fileGitHub
    <?php

declare(strict_types=1);

namespace Evalu8\Analysis;

/**
 * The instruction we send to any language model, so every provider is asked the same thing.
 */
final class CommentPrompt
{
    /** @param list<string> $comments */
    public static function for(array $comments): string
    {
        $lines = [];
        foreach ($comments as $comment) {
            $lines[] = '- ' . str_replace("\n", ' ', $comment);
        }

        return "Summarise these anonymous comments about a teacher in one short sentence. "
            . "Name the main topics. Do not quote anyone.\n\n" . implode("\n", $lines);
    }
}

  6. 6The OpenAI adapter

    It implements our interface, holds the SDK client, and translates in three places: the request, the result and the exception.

    src/Analysis/OpenAiCommentAnalyzer.phpnew fileGitHub
    <?php

declare(strict_types=1);

namespace Evalu8\Analysis;

use OpenAI\Client;
use OpenAI\Exceptions\ErrorException;

/**
 * Adapter: makes the OpenAI SDK look like a CommentAnalyzer.
 */
final readonly class OpenAiCommentAnalyzer implements CommentAnalyzer
{
    public function __construct(
        private Client $client,                             // the SDK object we adapt
        private string $model = 'gpt-4o-mini',
    ) {
    }

    public function summarize(array $comments): string
    {
        if (count($comments) === 0) {
            return 'no written comments';
        }

        try {
            $response = $this->client->chat()->create([      // our call → their call
                'model' => $this->model,
                'messages' => [
                    ['role' => 'user', 'content' => CommentPrompt::for($comments)],
                ],
            ]);
        } catch (ErrorException $e) {                       // their exception → ours
            throw new AnalysisFailed("OpenAI could not analyse the comments: {$e->getMessage()}", previous: $e);
        }

        return trim($response->choices[0]->message->content);    // their result → our string
    }
}

  7. 7The Ollama adapter

    Same interface, completely different inside. The error array becomes an exception here, so it can never be mistaken for a summary.

    src/Analysis/OllamaCommentAnalyzer.phpnew fileGitHub
    <?php

declare(strict_types=1);

namespace Evalu8\Analysis;

use Ollama\Client;

/**
 * Adapter: makes a self-hosted Ollama server look like a CommentAnalyzer.
 * Ollama's API is shaped differently (arrays, and errors returned instead of thrown);
 * all of that difference stays inside this class.
 */
final readonly class OllamaCommentAnalyzer implements CommentAnalyzer
{
    public function __construct(
        private Client $client,
        private string $model = 'llama3.2',
    ) {
    }

    public function summarize(array $comments): string
    {
        if (count($comments) === 0) {
            return 'no written comments';
        }

        $result = $this->client->generate([                 // our call → their call
            'model' => $this->model,
            'prompt' => CommentPrompt::for($comments),
            'stream' => false,
        ]);

        if (isset($result['error'])) {                      // their error array → our exception
            throw new AnalysisFailed("Ollama could not analyse the comments: {$result['error']}");
        }

        if (!isset($result['response'])) {
            throw new AnalysisFailed('Ollama returned no response text.');
        }

        return trim($result['response']);                   // their result → our string
    }
}

How Laravel does it

Storage::put() works on a local disk, S3 or FTP because of adapters: Laravel’s FilesystemAdapter translates its own methods into the Flysystem library’s, and each Flysystem adapter translates those into one storage SDK.

For your own vendors, bind your interface to the adapter in a service provider, with the SDK’s settings in config/services.php:

Laravel
// app/Providers/AppServiceProvider.php
$this->app->singleton(CommentAnalyzer::class, fn () => new OllamaCommentAnalyzer(
    new \Ollama\Client(config('services.ollama.host')),
    config('services.ollama.model'),
));

Check yourself

Answer in your head, then open the answer.

Google Gemini is added next year. What changes?

One new class, GeminiCommentAnalyzer implements CommentAnalyzer, and the binding. Nothing that uses CommentAnalyzer changes.

Why does the Ollama adapter turn the error array into an exception?

Otherwise the error could flow on as if it were a summary. Translating failures is part of the adapter’s job, just like translating calls and results.

How is an Adapter different from a Decorator?

An adapter wraps something with the wrong interface and only translates. A decorator wraps something that already has your interface and adds behaviour.

The adapter is chosen by editing bootstrap/app.php. Developers want Ollama on their laptops and production wants OpenAI for some schools, without code changes.
