Measure first: reproduce the load

Guessing at performance is how teams add the wrong index. The first step is to make the problem happen on purpose, somewhere safe: a staging server with a copy of production’s data (21,000 properties, 2.1 million bookings, guest names replaced). k6 sends searches at a fixed rate, like real traffic, and reports how long they took.

loadtests/search.js
import http from 'k6/http';
import { check } from 'k6';

export const options = {
    scenarios: {
        sunday_peak: {
            executor: 'constant-arrival-rate',    // 400 searches every second, however slow the answers get
            rate: 400,
            timeUnit: '1s',
            duration: '5m',
            preAllocatedVUs: 300,
        },
    },
    thresholds: {
        http_req_duration: ['p(95)<300', 'p(99)<800'],   // the run fails if search is slower than this
    },
};

const cities = ['Copenhagen', 'Aarhus', 'Skagen', 'Rørvig', 'Odense', 'Bornholm'];

export default function () {
    const city = cities[Math.floor(Math.random() * cities.length)];
    const response = http.get(`${__ENV.BASE_URL}/api/v1/search?city=${encodeURIComponent(city)}&check_in=2027-07-12&check_out=2027-07-19&guests=4`);

    check(response, { 'status is 200': (r) => r.status === 200 });
}

constant-arrival-rate matters: a test where each virtual user waits for its answer before the next request sends fewer requests as the server slows down, and hides the problem. Real guests don’t wait for each other.

The broken code

The slow query log and EXPLAIN point at the same line. The search from scene 30 filters by city first:

mysql
EXPLAIN SELECT id, name, city, max_guests FROM properties
WHERE city = 'Copenhagen' AND max_guests >= 4
  AND NOT EXISTS (SELECT 1 FROM bookings WHERE bookings.property_id = properties.id AND status IN ('pending', 'confirmed') AND check_in < '2027-07-19' AND check_out > '2027-07-12')
  AND NOT EXISTS (SELECT 1 FROM external_blocks WHERE external_blocks.property_id = properties.id AND starts_on < '2027-07-19' AND ends_on > '2027-07-12')
ORDER BY name LIMIT 50;

type ALL means MySQL reads every row of properties to find the ones in Copenhagen: the table has no index on city (the Foundation only indexed account_id). Using filesort means it then sorts the matches by name, by hand. The two subqueries are fine: they use their indexes (scene 30 and 32).

At 400 searches a second that is 8.5 million rows read every second, on the server that also takes every booking, payment and iCal sync. Search didn’t just get slow; it took the CPU the bookings needed.

The fix, part 1: one index that answers the WHERE and the ORDER BY

An index on (city, name) lets MySQL jump to Copenhagen and read its properties already sorted by name, so the sort disappears and it can stop as soon as it has 50 rows that pass the other conditions. max_guests stays out of it: as a range condition (>=), it would stop the index from also delivering the order.

The fix, part 2: reads go to a replica, decisions stay on the primary

Even fast searches are 400 queries a second that have nothing to do with taking bookings. A read replica is a second MySQL server that copies every change from the primary, usually within a second, and can answer SELECTs. Laravel sends reads there and writes to the primary when the connection has a read and a write host.

In config/database.php, replace the mysql entry inside connections with this one. The other connections stay as they are:

config/database.php (the mysql entry under connections)
'mysql' => [
    'driver' => 'mysql',
    'read' => [
        'host' => [env('DB_READ_HOST', env('DB_HOST', '127.0.0.1'))],  // the replica; locally the same server
    ],
    'write' => [
        'host' => [env('DB_HOST', '127.0.0.1')],                         // the primary
    ],
    'sticky' => true,                       // after a write, the same request keeps reading from the primary
    'port' => env('DB_PORT', '3306'),
    'database' => env('DB_DATABASE', 'laravel'),
    'username' => env('DB_USERNAME', 'root'),
    'password' => env('DB_PASSWORD', ''),
    'unix_socket' => env('DB_SOCKET', ''),
    'charset' => env('DB_CHARSET', 'utf8mb4'),
    'collation' => env('DB_COLLATION', 'utf8mb4_unicode_ci'),
    'prefix' => '',
    'prefix_indexes' => true,
    'strict' => true,
    'engine' => null,
    'options' => extension_loaded('pdo_mysql') ? array_filter([
        PDO::MYSQL_ATTR_SSL_CA => env('MYSQL_ATTR_SSL_CA'),
    ]) : [],
],

Which queries must still read the primary

A replica is a little behind. That is fine for a search (a hint, scene 30) and wrong for anything that decides. Laravel already sends these to the primary, and the table says why each one is safe:

QueryReads fromWhy
Search, quote page, properties pagereplicaA second-old view is fine; the booking checks again
The availability check in CreateBooking, ChangeBookingDates, MoveBookingprimaryThey run inside DB::transaction(): Laravel uses the write connection for every query of an open transaction
lockForUpdate() readsprimaryAlways inside those transactions; a lock on a replica would lock nothing
A read in the same request after a writeprimarysticky: true: the host who just saved a price sees it at once
Queue jobs (webhooks, imports, sends)replica, unless in a transactionEvery job here that decides something locks a row inside a transaction first (scenes 8, 15, 22)

For the rare read that must be fresh outside a transaction, ask for it: Booking::query()->useWritePdo()->find($id).

The same k6 run, with both fixes, passes its thresholds with room to spare, and the primary has its CPU back for bookings. The k6 script runs again before every peak season, against staging, so the next missing index shows up in a test instead of on a busy Sunday.

TestsThe search query uses the index and never sorts by hand
tests/Feature/SearchQueryPlanTest.phpnew file
<?php

use App\Bookings\Stay;
use App\Models\Property;
use Illuminate\Support\Facades\DB;

it('finds the properties of a city through the index, already sorted', function () {
    Property::factory()->count(30)->create(['city' => 'Copenhagen']);
    Property::factory()->count(30)->create(['city' => 'Aarhus']);
    DB::statement('ANALYZE TABLE properties');                                  // fresh statistics, like a production table has

    $search = Property::query()
        ->where('city', 'Copenhagen')
        ->where('max_guests', '>=', 4)
        ->availableFor(Stay::fromDates('2027-07-12', '2027-07-19'))
        ->orderBy('name')
        ->limit(50);

    $plan = collect(DB::select('EXPLAIN ' . $search->toRawSql()))->firstWhere('table', 'properties');

    expect($plan->key)->toBe('properties_city_name_index')
        ->and($plan->Extra ?? '')->not->toContain('filesort');                 // the incident: no full scan, no sort by hand
});

This test reads MySQL’s plan on purpose. With 60 rows MySQL could still choose a full scan; ANALYZE TABLE gives it real statistics so it picks what production picks. If someone drops the index or changes the query so the index can’t serve it, this test fails long before the next busy Sunday.
